# 时钟算法评价（两次 10 min NTP 比对）

> 依据：[ntp_cmp_test_20260911.md](ntp_cmp_test_20260911.md)、[ntp_cmp_test_20260914.md](ntp_cmp_test_20260914.md)、[local_clock_gps_check.md](local_clock_gps_check.md)  
> 固件：`LocalClock`（PPS 秒尺 + NMEA 交叉检核）及 2026-09-13 起的伺服收紧  
> 日期：2026-09-14

## 总评

在 **ESP32-C3 + 廉价晶振 + Wi‑Fi NTP 测法** 下，当前时钟算法已经达到设计目标，不必再为「把 offset stdev 再压 1 ms」改伺服。

| 维度 | 评价 | 依据 |
|------|------|------|
| 诚实授时 | **优** | 9/14 搜星阶段 stratum 16 / LI=3 / `INIT` / dispersion 65535 s；锁定后立刻 stratum 1 / `GPSS` |
| 锁定后相位 | **优** | 两次锁定段 `residualMs=0`、`ppsFresh=true`；干净 RTT 下 offset stdev **1.3～2.6 ms** |
| 无整秒跳变 | **优** | 相对历史 51.3% 错秒，两次 10 min **0 次** \|GPS−阿里云\| > 400 ms |
| 对公网粗参考 | **通过** | 锁定后 diff 中位 −3～−7 ms；9/14 范围仅 −20～+29 ms |
| 守时 / 拔天线 | **未现场验收** | Holdover 色散、Refuse→UNS 只有代码路径 |
| 对 UTC 的绝对误差 | **本测法不能下结论** | 看到的是客户端钟差 + Wi‑Fi 路径，不是 GNSS 真值 |

**产品表述：** 局域网 Stratum-1 GNSS NTP，客户端体感约 **1～10 ms**。不是电信/PTP/金融同步，也不是「误差 1 ms」的广告语。

## 测法边界（评价必须先认）

`offset_ms` 是「服务器相对这台客户端」。里面叠了：

1. 客户端系统钟相对 UTC 的慢/快（9/11 PC ≈ −243 ms，9/14 手机 ≈ +24 ms）
2. 客户端↔设备（或公网）的不对称时延
3. Wi‑Fi 排队/重传（9/14 有 9 次 delay 38–81 ms，offset 跟着跳到 36–61 ms）
4. 设备真实相位（我们真正关心的）

因此：

- **stdev / 相邻步长** 才能谈稳定性；绝对 offset 只描述客户端钟差。
- 9/14 引用稳定性应报 **delay &lt; 20 ms** 的 1.34 ms，不要报含尖峰的 9.16 ms。
- 亚毫秒/微秒级只能靠 PPS 对拍或有线硬件时间戳，这两次都没有。

## 分项：优化是否被数据撑住

### 1. 未锁定不授时（Phase A）

设计：`nowUtc()` 只在 LCK/DEG/HLD 返回；NTP 未同步时 LI=3、stratum 16、refid `INIT`、dispersion 拉满。

比对 B 前 5 轮原样出现上述字段，offset 落到 −4×10¹² ms 量级（未同步时间基，不是「慢了 4 百万秒」）。第 6 轮起变为 LI=0 / stratum 1 / `GPSS` / dispersion ≈ 5–6 ms。

**评价：** 这是 9/13 诚实化之后最硬的现场证据。旧病是「模块还没锁也当优质 stratum 1」。现在客户端在搜星阶段不会被骗去校时。

比对 A 开跑时已经 LCK，测不到这一条。

### 2. PPS 走相，NMEA 只做检核

设计：锁定后每个稳定 PPS 把锚点 `utcSec+1`；NMEA 在 **PPS 边界**算 residual；Locked 且 \|r\| &lt; 5 ms 不重锚，避免 NMEA 解析抖动抬高 std。

两次锁定段 **`residualMs` 全程 0**（10 s 采样）。比对 A stdev 2.63 ms、步长中位 1.11 ms；比对 B 干净样本 stdev 1.34 ms、步长中位 0.98 ms。没有秒级台阶，也没有「每秒被 NMEA 拽一下」的锯齿。

**评价：** 5 ms slew 带和 PPS 走相同向。residual 恒 0 说明交叉检核认为相位已贴在整秒上；对外 NTP 起伏被测法底噪盖住（1–3 ms），再抠伺服收益极小。

### 3. 估频（8 s 跨度 + EMA）与冷启

设计：边沿环最近 8 个 1 s 间隔平均再 EMA（α=0.2）；间隔门限 5 ms；冷启要连续好间隔才 `ppsStable_`，不在首个孤边沿建锚。

比对 B 从脚本视角约 50 s ACQ 后进入 LCK（不知上电已多久，只能说「未锁时不会提前 stratum 1」）。比对 A 与 9/11 冒烟：冷启约 90 s → LCK，当时 `freqPpm≈−0.4`（廉价 XO 的正常量级）。

锁定后 root dispersion 钉在 **~6 ms**（quality 地板约 5 ms + 微小 ppm 加成），没有随时间爬升——说明 **没有进入 Holdover/Degraded**，估频也没有把 quality 顶上去。

**评价：** 8 s 跨度足够滤掉单间隔量化噪声；现场没有「锁上又掉、dispersion 乱飘」。温度 trim 默认关，这两次都 **没有** 验证 `tcmp`。

### 4. 相对阿里云

| | 比对 A（伺服初版） | 比对 B（收紧后） |
|--|-------------------|------------------|
| 配对 | 60（全程 LCK） | 52（LCK；阿里云超时 3） |
| diff 中位 | −3.34 ms | −6.63 ms |
| diff 范围 | −20～**+253** ms | −20～**+29** ms |
| \|diff\| > 400 | 0/60 | 0/52 |

+253 ms 那次 GPS offset 仍贴着 −242 ms 基线，是 **云路径尖峰**，不是设备跳秒。比对 B 云侧更老实，两边粗一致性约 ±20 ms。

验收门槛（设计文档）：`|diff| > 400 ms` 仍为 ~0%，std 不明显恶化。  
**两次都通过。** 收紧后没有把稳定性做坏；B 的「更好」主要是云侧碰巧没尖峰 + 滤了高 RTT，不能单独归功于 8 s 估频。

### 5. 历史病已经闭环

| 阶段 | 现象 |
|------|------|
| 修复前 | 异常率 51.3%，stale 整秒 −1 s → −3～−4 s |
| RTOS + PPS-count 对齐后抽测 | 异常率 0%，配对差中位 ~48 ms |
| LocalClock 初版 + 比对 A | 10 min 无整秒跳；PC 测 stdev 2.6 ms |
| 伺服收紧 + 比对 B | 诚实 INIT→GPSS；干净 stdev 1.3 ms；仍无 400 ms 级异常 |

整秒错标是已消灭的旧 bug。当前算法是在「已经能对上秒」之上，加上 **可见健康度** 和 **宁可拒报**。

## 没有被这两次测到的部分

这些优化在代码里，但 CSV **给不出分数**：

- **HoldoverShort/Long**：色散随 ppm×age 增长、超时/质量超 500 ms 转 UNS  
- **Refuse + 拔天线**：应迅速 LI=3，不得假 stratum 1  
- **Degraded（residual 50–100 ms）**：WARN 不重锚、只抬 dispersion  
- **温度补偿**：默认关；片上 TSENS 只是晶振代理，本来就是粗 trim  
- **长 holdover 守时误差**：廉价 XO 按 50 ppm 地板，5 min 理论可漂约 15 ms；未测  
- **PPS 对 UTC 的绝对相位**：Wi‑Fi NTP 看不到 µs

设计文档里「拔天线策略差异」仍待现场；**≥10 min vs 阿里云回归可以勾掉。**

## 还要不要继续改算法

| 想法 | 建议 |
|------|------|
| 再加大 ppm 平滑 / 再加 PLL | **不必。** 测法底噪已是 1–3 ms，现场看不出 |
| 默认打开温度补偿 | **先不要。** 未对照；系数 −0.50 ppm/°C 是猜的。要开就单独做一夜对比 |
| 默认 Holdover 代替 Refuse | **产品选择，不是精度问题。** Refuse 更诚实；室内偶发遮挡才值得 Short |
| 宣称亚毫秒 | **不要。** 除非示波器对 PPS 或有线硬件时间戳 |

值得做的现场，按性价比：

1. 锁定后拔天线：Refuse 应变 UNS；HoldoverShort 应 HLD 且 dispersion 上升  
2. 冷启到 LCK 计时（UART/`/status`），确认 8 s 稳 PPS + 3 次 relock 的量级  
3. 需要守时再考虑开 `tcmp` 做对照，而不是先改 EMA

## 一句话

两次 10 分钟比对加上 9/13 的伺服收紧，说明这套时钟 **锁得住、不说谎、锁后不抖**，已经匹配硬件与产品定位。剩下的是异常策略的现场验收，不是把毫秒级 NTP 曲线再磨尖。

关于「把 23 ms 当处理延迟扣掉 / 再挪时间戳」的评估见 [ntp_timestamp_eval.md](ntp_timestamp_eval.md)：**23 ms 是客户端钟差；用户态打戳位置已经基本正确。**
