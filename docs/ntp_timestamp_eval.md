# NTP 时间戳位置与「固定 23 ms」评估

> 状态：**只评估，不实现**  
> 日期：2026-09-14  
> 依据：`src/ntp_server.cpp` 现网路径；[ntp_cmp_test_20260911.md](ntp_cmp_test_20260911.md)、[ntp_cmp_test_20260914.md](ntp_cmp_test_20260914.md)、[clock_eval_two_ntp_cmp.md](clock_eval_two_ntp_cmp.md)

两条外部建议：

1. **校准固定 offset**：把稳定的约 23 ms 偏差，从 NTP 回复里扣掉「实测处理延迟」，以提升精度。  
2. **优化时间戳位置**：把 Receive / Transmit 打得更贴近「包进 / 包出」。

结论先说：**建议 1 按字面做会损害诚实授时，23 ms 不是处理延迟。建议 2 方向对，但本项目已经做对了用户态该做的大部分，剩余收益在亚毫秒～数毫秒，且被 Wi‑Fi 协议栈封顶。**

---

## 1. 建议 1：扣 23 ms / 扣处理延迟

### 1.1 那 23 ms 是什么

2026-09-14 Termux（锁定、delay &lt; 20 ms）：

| 量 | 中位 |
|----|------|
| GPS `offset` | **+24.0 ms** |
| GPS `delay`（RTT） | **7.5 ms** |
| 阿里云 `offset` | **+31.2 ms** |
| 阿里云 `delay` | **65 ms** |
| GPS − 阿里云 | **−6.6 ms** |

2026-09-11 同一台设备、另一台 Windows PC：GPS `offset` 中位 **−243 ms**，delay 中位 5.3 ms。

同一套固件、两个客户端，绝对 offset 差一个数量级、符号相反。这只能是 **客户端系统钟相对 UTC 的慢/快**，不是设备里有一个固定 23 ms 处理税。

更硬的否证：

- NTP 往返 **delay ≈ 7.5 ms**。处理延迟若真有 23 ms，会直接出现在 RTT 里，不可能「delay 7.5、offset 却稳 23」。  
- 同一只手机看阿里云也是 **+31 ms**。若在 GPS 回复上减 23 ms，手机上 GPS 会变成约 +1 ms，阿里云仍是 +31 ms，**两边差 30 ms**，比现在的 −6.6 ms **更差**。  
- 若把 −23 ms 写进所有回复，9/11 那台已经慢 243 ms 的 PC 会变成约 −266 ms；任何已经用 chrony/ntpd 对准的局域网机器会被 **拉偏 23 ms**。

### 1.2 处理延迟在公式里本来就不进 offset

经典四戳：

```
offset = ((T2 − T1) + (T3 − T4)) / 2
delay  = (T4 − T1) − (T3 − T2)
```

`T3 − T2` 是服务器处理时间。两边打戳只要来自同一把 LocalClock，**处理时间进入 delay，不进入 offset**。再从 T2/T3 上减一遍 `(T3−T2)` 或减一个常数 23 ms，等于人为把服务器钟拨快/拨慢，对「这只未校准的手机」好看，对其它客户端作假。

本项目用户态处理（`parsePacket` 之后：读 48 字节、ACL、速率表、组包、再 `nowUtc`）在 C3 上是 **百微秒～一两毫秒** 量级，不是 23 ms。现网 **没有** 把 `T3−T2` 打进 CSV，所以「实测处理延迟」目前也测过。

### 1.3 什么情况下「减一个数」才合法

只有对着 **比 Wi‑Fi NTP 更真的参考**（示波器对 PPS、有线硬件时间戳、同机房 stratum-1）量出设备钟的 **固定相位误差**，才可以谈校准。手机 vs 设备 vs 阿里云 **不是** 这种参考。

即便将来 PPS 对拍量出例如 +80 µs 的天线/电缆/固件偏置，那是 **相位校准常数**（写进 LocalUtc 或只加在 T2/T3），不是「处理延迟」，也绝不是这次的 23 ms。

### 1.4 建议 1 的裁决

| 做法 | 裁决 |
|------|------|
| 把 +23 ms 当固件常数从回复里减掉 | **否决。** 校准到这只手机，破坏其它客户端和诚实性 |
| 用 `(T3−T2)` 去改 T2 或 T3 | **否决。** 公式已处理；再减是双重计数 |
| 日志里打出 `T3−T2`，确认用户态处理 &lt; 2 ms | **可做，观测项**，不改授时 |
| PPS 对拍后再谈 µs 级相位常数 | **以后的事**，与本次 23 ms 无关 |

## 2. 建议 2：优化时间戳位置

### 2.1 现在打在哪

`NtpServer::handlePacket` / `sendNormal`（`task-time`，1 ms 轮询 + PPS notify）：

```
parsePacket()          ← 包已在 lwIP 套接字里（Wi‑Fi RX 栈延迟已经发生）
nowUtc() → T2          ← Receive Timestamp（读 payload 之前，用户态尽可能早）
read 48B
ACL / 限速
组包（LI/stratum/dispersion/ref/org）
把 T2 写入 Receive
nowUtc() → T3          ← Transmit Timestamp
beginPacket + write + endPacket   ← 之后还有 lwIP / Wi‑Fi TX 栈
```

对照「理想位置」：

| 戳 | 理想 | 现状 | 偏差方向 |
|----|------|------|----------|
| T2 Receive | 包到达网卡 / 驱动 RX | `parsePacket` 之后立刻 `nowUtc` | **偏晚**（Wi‑Fi RX + 任务最多约 1 ms 调度） |
| T3 Transmit | 包离开网卡 / 已交给驱动 TX | 组包后、`beginPacket` 前 `nowUtc` | **偏早**（TX 栈还没走） |

用户态顺序 **已经基本正确**：T2 在 `read`/ACL/限速之前；T3 在组包之后、发送之前；T2≠T3。这比「收发共用一个戳」或「读完、限速完才打 T2」要好。

### 2.2 晚 T2 / 早 T3 对客户端的影响

- T2 偏晚 `d_rx` → offset 大约 **+ d_rx / 2**（设备显得快）  
- T3 偏早 `d_tx` → offset 大约 **− d_tx / 2**（设备显得慢）  
- 二者接近时大致对消；Wi‑Fi 上往往 RX 排队更肥，可能剩 **+0.5～数 ms** 的系统偏置  

这解释得了「干净样本里 1～3 ms 的测法起伏」，**解释不了稳定的 +24 ms**（且阿里云同样 +31 ms）。

`precision` 在 PPS 就绪时已是 −10（≈1 ms），和这条残差同一量级，元数据没有吹牛。

### 2.3 还能往哪挪（按侵入性）

| 档 | 做法 | 预期收益 | 代价 / 风险 | 建议 |
|----|------|----------|-------------|------|
| A | T3 挪到 `write` 之后、`endPacket` 之前 | 百微秒 | 几行，几乎无风险 | **若动手，只做这一档** |
| B | `parsePacket` 成功后第一件事只读 `esp_timer`，组包时再换成 UTC | 与现在几乎相同（`nowUtc` 已是 `esp_timer` 外推） | 无实质收益 | 不做 |
| C | 缩短 `parsePacket` 到处理的调度：PPS/NMEA 后再 `ntp.loop` 的顺序已是先 GPS 后 NTP；C3 单核无法并行 | 偶发 1 ms 级 | 已是 prio 5 + 1 ms 票 | 维持现状 |
| D | lwIP / `WIFI_EVENT` / 驱动 RX 回调里打 T2 | 或许可再挤 0.5～2 ms | 要绕开 Arduino `WiFiUDP`；ISR/回调里不能重活；和现架构「任务内打戳」冲突；难测 | **不做**（C3 + Arduino 不值） |
| E | 硬件时间戳 / PTP | µs | C3 Wi‑Fi 无可用 PTP；已划为非目标 | **不做** |

A 的收益远小于测法底噪（手机/PC Wi‑Fi NTP 1–3 ms），**单独做看不出 CSV 变好**。它的价值只是「顺序更教科书」，不是精度跃迁。

## 3. 和项目约束的对齐

- **诚实 NTP（Phase A）**：未锁定 `INIT`；锁定后 T2/T3 必须是 LocalUtc，不能为了某只手机减常数。  
- **C3 单核**：时间戳再往驱动里塞，会和 PPS ISR、UART1 抢同一核，收益不确定。  
- **产品定位**：局域网 1～10 ms，不是机架 µs 钟。建议 1 若落地，广告上会变成「对着我的手机校过」，和文档承诺相反。  
- **测法**：要证明「打戳位置」有效，必须 **同一客户端、改前/改后、看 delay 分布和 T3−T2**，不能看绝对 offset 是否靠近 0。

## 4. 方案（仍不实现，除非以后单独立项）

### 不做

1. 任何形式的「−23 ms」或「按某次 Termux 中位数校准」。  
2. 用 `(T3−T2)` 去改对外时间戳。  
3. 驱动/lwIP 级 RX 时间戳、硬件 TS。

### 若以后要动，按这个顺序

1. **观测（推荐，低风险）**  
   - 在 `sendNormal` 里用已有的 T2/T3 算 `procUs`，UART 或 `/status` 打 p50/p95（不要写进 NTP 包）。  
   - 预期：锁定时空载 p50 &lt; 1 ms，p95 &lt; 3 ms。若真出现经常 &gt; 5 ms，再查限速表或 GPS `loop` 是否挡住 `ntp.loop`。  
   - 复测仍用 `tools/ntp_cmp_termux.py`，**只看 delay 与步长，不看 offset 是否靠近 0**。

2. **打戳微移（可选，档 A）**  
   - T3 紧贴 `endPacket` 之前。  
   - 不改 T2 语义（保持 `parsePacket` 后第一时间）。  
   - 验收：`procUs` 略增（把组包算进处理，这是对的）；客户端 offset stdev **不应明显变**；`|GPS−阿里云|` 中位仍 &lt; 50 ms。

3. **相位校准（仅当有真参考）**  
   - PPS 对拍或有线参考之后，才能谈 `phaseOffsetUs` 写入 LocalClock。  
   - 与「处理延迟」分字段，禁止和 23 ms 混用。

### 验收红线

- 禁止让「这只手机 offset≈0」成为通过条件。  
- 禁止改变未锁定时的 LI=3 / stratum 16 / `INIT`。  
- 禁止为打戳把重活放进 ISR。

---

## 5. 一句话

**23 ms 是手机钟，不是设备税；扣它会让 NTP 对其他客户端说谎。时间戳位置值得保持「早 T2、晚 T3」，但现在已经在用户态该停的地方，再往下是 Wi‑Fi 栈，不是再减一个常数能解决的。**
